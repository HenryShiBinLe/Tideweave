# 脉序 · Tideweave 云同步技术方案

负责：@HenryShiBinLe（与 Claude Code 协作）　状态：合并逻辑、服务端、客户端收发已完成并通过测试；服务已部署到美国 VPS，外网可访问，晚高峰实测后决定要不要换国内服务器；同步调度、前端接入待做　更新：2026-10-18

本文写的是云同步这一侧怎么实现。双方接口（存档结构、各字段怎么合并、关卡 ID 和修订号的约束）以 [协作约定-存档与云同步.md](协作约定-存档与云同步.md)（下称“约定”）为准，本文不重复，只补充实现细节。约定改了，本文跟着改。

> **TL;DR**
>
> 1. **服务端不懂游戏**：只按同步码存取一份“信封”（存档 + 同步层自己记的时间），带版本号，保留历史版本。合并全在设备上做。
> 2. **离线优先**：存档永远先写本地，同步在后台进行。断网、服务挂了、合并出错，游戏都照常玩，本地进度不受影响。
> 3. **防覆盖**：推送时带上拉取时的版本号；期间有别的设备推送过，就重新拉取、合并、再推送。
> 4. **部署**：先部署在现有的美国 VPS 上（10/18），晚高峰用手机实测；不够好再换国内服务器（Node + systemd，未备案只能用 `http://IP:端口` 访问）。网页版和接口放在同一个地址下（正式托管网页版要先和 @aliezXDD 确认）。
> 5. **范围**：先接 Web 版；Windows 桌面版保持离线；Mac 版以后再说。

## 一、总体结构

```
网页版 main.mjs ──save()/load()──▶ src/sync/
                                     1. 先写 localStorage，和现在完全一样
                                     2. 后台：拉取 → 合并 → 应用 → 推送
                                            │ HTTP(S) + JSON
                                            ▼
国内服务器：server/（Node，零依赖）──▶ 数据目录（每个同步码一份信封 + 历史版本）
```

合并放在设备上（约定第一部分已定），理由：

- 只有游戏代码能验证方案、复用 `recordAttempt()` 评优；
- 服务端不依赖游戏代码，玩法怎么改都不用重新部署服务端；
- 新旧版本的设备各自验证自己认识的关卡，不认识的原样保留云端的。

不用 Firebase、Supabase、Cloudflare Workers 这类现成服务：国内访问没有保障，还要注册账号。

## 二、云端数据：信封

```json
{
  "format": 1,
  "save": { "version": 1, "records": {}, "last": "01-02.3", "chapter": 1, "summaries": [], "briefings": [], "settings": {} },
  "clock": { "fields": { "records/01-02.3/state": 1760710000000, "last": 1760710000000 }, "savedAt": 1760710000000 },
  "device": "d-7f3a9c"
}
```

- `save`：合并后的**原始存档**（约定：推回云端的不经过 `normalize()`），服务端不解析。
- `clock`：同步层自己记的修改时间（约定：时间不进存档）。`fields` 只记现场型字段：每关的 `state`、`last`、`chapter`。某字段没有单独记录时用 `savedAt`（整份存档的时间）兜底，都没有就按最旧处理。
- `device`：最后写入的设备，只用来排查问题。
- 大小：49 关全部通关、最佳方案和编辑现场都填满的存档，实测 27 KB。服务端沿用约定的 4 MB 上限。

## 三、接口

同步码放在请求头 `X-Sync-Code` 里，不放进 URL，免得被写进访问日志。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/save` | 返回信封，响应头带 `ETag: "版本号"`。没有返回 404；带 `If-None-Match` 且没变化返回 304 |
| PUT | `/api/v1/save` | 推送信封。必须带 `If-Match: "版本号"`，首次创建用 `If-None-Match: *`，两个都没带返回 428。版本号对不上返回 412（附当前版本号）；云端存档版本更高返回 409；超过大小返回 413；格式不对返回 400；太频繁返回 429；新建时服务器磁盘不足返回 507 |
| GET | `/api/v1/save/versions` | 历史版本列表（版本号、时间、大小、设备）。回滚用服务器上的运维脚本，不做界面 |
| GET | `/api/v1/health` | 健康检查 |

服务端只校验这些：`format === 1`；`save` 是对象，`save.version` 是支持的版本（现在只有 1），`save.records` 是对象；请求体不超过 4 MB。不看进度内容。

## 四、同步流程

**一次同步**：

1. 拉取云端信封，记下版本号；
2. `merge(本机, 云端)`，得到“推回云端的原始存档”和“本机要用的存档”；
3. 本机进度有变化：先备份本机存档，再应用（见下）；
4. 云端需要更新：带 `If-Match` 推送。收到 412 就回到第 1 步，最多 3 次；
5. 更新同步状态：已同步（时间）/ 同步中 / 离线，稍后重试 / 需要更新游戏 / 出错。

**什么时候同步**：启动时；存档后 5 秒内没有新改动时；切回页面时；页面在前台时每分钟拉一次；网络恢复时。失败后退避重试，从 5 秒开始，最长 5 分钟。

**应用云端进度**：按约定第六部分，沿用导入存档的处理（停止播放、清空 `sessionCache`、替换存档、保存、重画），只在玩家不在关卡里时执行；在关卡里就等退出后再应用。

**开启方式**：在设置里“开启云同步”会生成新同步码；在另一台设备上“输入同步码”。输入的同步码在云端不存在时，提示检查输入，不会悄悄新建，免得输错一位就同步到一个空码上。

## 五、合并算法

输入：本机 `{save, clock}`，云端 `{save, clock}`（可能没有）。输出：推回云端的 `{save, clock}`、本机要用的 `{save, clock}`（`save` 已经过 `normalize()`），以及两边是否有变化。实现在 `src/sync/merge.mjs`，是纯函数，可以在 Node 里测试。

字段规则按约定第二部分的表。下面是表里没细说、实现时要定的地方：

1. **版本**：云端 `save.version` 比本机高，暂停同步、不推送；不是 1 也不更高，视为不兼容，同样不推送。
2. **逐关处理**，遍历两边关卡 ID 的并集：
   - **本机不认识的关卡**：原样保留，两边都有时取云端的。
   - **任一边修订号比本机当前修订号高**（来自更新版本的设备）：本机验证不了。推回云端的保留修订号高的那份，本机继续用自己的记录。本机看不到新题的进度，但也不会被它覆盖掉自己的成绩。
   - **只有一边有记录**：照抄，`normalize()` 读档时会清洗。
   - **两边都有**：先把两边“提升”到当前修订号，口径和 `normalize()` 读档迁移完全一致：修订号不同的那份，它的 `legacyBest`（没有就用 `best`）作为旧版成绩候选，编辑现场作废。然后：
     - `best`：用当前题目验证两边的候选，只在通过的里面比较；
     - `legacyBest`：用旧题（`legacyLevelById`）验证所有旧版成绩候选，再比较；
     - `state`：在修订号等于当前修订号的记录里，取修改时间较新的；
     - `attempts` 取较大，`hintUnlocked` 任一为真即为真；
     - `passed`、`perfect`、`bestMetric`、`legacy` 按 `normalize()` 的口径重新算出。这只是让原始存档前后一致，读档时 `normalize()` 还会再算一遍。
3. **评优**：不另抄规则，直接复用 `recordAttempt()`（约定第四部分）：在一份临时存档上把方案 A 设为最佳，用方案 B 调用一次，看最佳方案有没有被换成 B。候选按“云端在前”排列，平局保留云端的，所以两台设备反复同步不会来回替换同分的方案。“完美”的定义是通过且指标等于最优值（`engine.mjs` 的 `evaluate()`），所以按这个规则，完美方案不会被不完美的方案顶掉。
4. **保留原始数据**：选中的方案和编辑现场按原样存，不存 `cleanState()` 清洗后的版本。这样新版本设备在方案里加的字段，不会被旧设备删掉。
5. **现场型字段**（`state`、`last`、`chapter`）：比较修改时间，取较新的；时间相同取云端的。选中那份的时间写进合并后的 `clock`。
6. **未知字段**（顶层或单关记录里本模块不认识的字段）：只有一边有就照抄；两边都有，取 `savedAt` 较新的一边。
7. **其余**：`summaries`、`briefings` 取并集（去重、排序）。`settings` 不同步：推回云端的沿用云端原有的，本机用自己的。
8. **自检**：合并后对本机要用的存档跑一次 `normalize()`，检查原来在本机或云端已通过（或已完美）的关卡，合并后仍然通过（或完美）。不满足就放弃这次同步，不推送，并报错。这是防止合并逻辑本身出错的最后一道闸。
9. **确定性**：同样的输入总得到同样的输出；用合并结果再合并一次不会产生变化；两台设备轮流同步，最后会收敛到同一份。

## 六、出错与恢复

- **离线、服务挂了**：本地照常存，状态显示“离线”，退避重试。同步层的任何异常都只影响同步状态，不影响游戏。
- **合并或 `normalize()` 出错**：保留本地，不推送（约定第六部分）。
- **云端版本更高**：暂停同步，提示更新游戏；服务端也拒绝用低版本覆盖高版本（409）。
- **本机备份**：应用云端进度前，把当前本机存档存到 `tideweave-sync-backup`。
- **服务端历史版本**：每个同步码保留最近 20 个版本，外加近 7 天每天 1 个。只留最近 20 个的话，连续操作几分钟就会被新版本挤掉。回滚用 `node server/admin.mjs restore <同步码> <版本号>`，把旧版本作为新版本写回。

## 七、安全

- **同步码**：12 位 Crockford Base32（去掉容易混淆的 I、L、O、U），约 60 bit 随机数，显示成 `XXXX-XXXX-XXXX`。在浏览器本地用 `crypto.getRandomValues` 生成（HTTP 页面也能用），断网也能开启。输入时不区分大小写，忽略空格和横线。
- **服务端只存同步码的 SHA-256**：即使数据目录泄露，也拿不到同步码。
- **限流**：按 IP 和按同步码分别限流，新建同步码单独限流。默认额度按“一个班在同一个校园网出口 IP 后面一起玩”估算：每个 IP 突发 120 次，之后每秒 2 次；每个同步码的推送突发 10 次，之后每 3 秒 1 次；每个 IP 新建同步码突发 30 个，之后每分钟 1 个。请求体上限 4 MB；磁盘剩余空间不足时拒绝新建同步码。
- **CORS**：白名单可配置（本机预览 `http://127.0.0.1:*`、`http://localhost:*`，以及正式网页地址）；同源托管时用不到。
- **数据敏感度**：存档里只有进度和设置，没有个人信息，泄露了代价也低，所以不做账号体系。用 HTTP 明文时同步码可能被截获，有条件就上 HTTPS。

## 八、部署

**现状（10/18）**：先部署在现有的美国 VPS（31.58.87.41，HOSTVDS 弗里蒙特）上，用 agent 账号运行：Node 装在用户目录，`server/run-user.sh` 负责常驻和崩溃重启，crontab 负责开机自启；监听 8080 端口，同时托管网页版和测速页（内部测试，不算发布）。服务器开着 ufw，8080 已由 @HenryShiBinLe 放行（只放 TCP）。下午非高峰从国内直连实测（家里宽带）：延迟 170 毫秒，20 个包零丢包；第一次打开游戏（首屏 4 个文件约 0.5 MB）1.4 秒，同步一次（拉取 + 推送 27 KB）约 0.8 秒。今晚 20～22 点用手机流量打开测速页实测：首次打开游戏和同步一次都在几秒以内，就不换服务器；明显卡顿或连不上，再买国内服务器。

为什么可以先不换：压测说明算力绰绰有余；同步在后台进行、先存本地，170 毫秒的延迟玩家感觉不到。真正需要国内服务器的情况只有三种：要让别人在国内直接打开网页版、而晚高峰跨境线路太慢；担心这个 IP 在国内访问不稳定或被封；担心和这台机器上的其他服务互相影响。美国服务器反而不用备案，以后要上 HTTPS 更方便。

**备选：国内服务器**（晚高峰实测不理想时再买）。推荐雨云 KVM 中配版（2 核 4 GB，上传 20 Mbps）：压测显示 CPU 和内存都远超需要，唯一可能的瓶颈是很多人同时打开网页时的上传带宽，而这一档的带宽在雨云这排套餐里已经是最高。预算紧可以选标配版（2 核 2 GB，上传 15 Mbps）。地域选国内 BGP（三网）线路，离北京越近越好；必须有独立公网 IPv4。

**约束**：

- **备案**：大陆服务器只要绑域名、走 80/443 端口，就必须先做 ICP 备案，一般要一到三周，10/22 前来不及。所以先不绑域名，用 `http://IP:端口` 访问。平台一般按域名拦截，IP 直连通常不受影响，部署后实测。
- **HTTPS**：可以试 Let's Encrypt 的 IP 证书（`shortlived` profile，约 6 天有效，由 ACME 客户端自动续期，签发时要放行 80 端口做验证）；试不通就先用 HTTP。
- **同源**：HTTPS 页面不能调用 HTTP 接口（浏览器会当作混合内容拦掉），所以没有 HTTPS 时，网页版必须和接口放在同一个地址下。服务端可以顺带托管 `dist/`：gzip 后约 0.5 MB，3 Mbps 带宽约 1.5 秒加载完。是否托管网页版要和 @aliezXDD 确认（约定：Web 部署另行商量）。
- **不用 Docker**：国内服务器拉 Docker Hub 镜像通常不通。服务端零依赖，从 npmmirror 下载 Node，用 systemd 常驻，并用单独的系统用户运行。

**步骤**（服务器到位后，具体命令见 [server/README.md](../Tideweave/server/README.md)）：安全组放行 22 和对外端口（试 IP 证书的话再放行 80）→ 配置 SSH 公钥登录 → 从 npmmirror 装 Node 24 → 上传 `server/`，装成 systemd 服务（`server/tideweave-sync.service`，用单独的 `tideweave` 用户运行）→ 用手机流量实测访问速度和延迟。
