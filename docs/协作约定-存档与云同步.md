# 脉序 · Tideweave 协作约定：存档与云同步

参与：@aliezXDD（玩法、关卡、界面，作品主体）、@HenryShiBinLe（云端存档同步）

依据代码：`main` 分支 `ec4e4a4`（10/17）。存档相关代码以后有变化，本文按最新代码更新。

> **TL;DR**
>
> 1. **分工**：作品以 @aliezXDD 的 Tideweave 为准。@HenryShiBinLe 负责云端存档同步，包括同步服务端和合并逻辑；除了第六部分约好的前端接入那几处，只新增文件，不改 @aliezXDD 的文件，也不改玩法、判定、关卡和界面。云同步目前还在设计阶段，尚未实现。
> 2. **范围**：只约定和存档、同步有关的部分。同步先接 Web 版，之后是 Mac 版；Windows 桌面版保持离线。前端只约定接入同步时的范围和方式（第六部分），具体时间另行商量。
> 3. **接口**：现有的存档结构就是双方之间的接口，每个字段同步时怎么合并见第二部分。需要 @aliezXDD 注意 6 条（第三部分）：关卡 ID 不改；已发布的题要改判定相关的内容就升修订号，历史题目要留着；存档结构变化要升版本；新增存档字段说明同步方式；判定保持确定性；规则和存档模块保持能在 Node 里运行。
> 4. **评优**：两份最佳方案哪个更好，只在 `recordAttempt()` 里维护，合并时直接复用，@aliezXDD 不需要为同步改代码（第四部分）。
> 5. **自动检查**：每次发布时，@HenryShiBinLe 存一份发布基线并加测试，`npm test` 会检查已发布的题有没有被改动（第三部分第 2 条）。
> 6. **记录**：改关、修订号、存档字段的变化和每次发布，记在 `GAMEPLAY_CHANGES.md`。

## 一、同步怎么工作

1. 每个玩家有一个同步码，服务端按同步码保存一份存档。服务端只检查格式版本和大小，不解析里面的进度。
2. 设备同步时，先拉取云端那一份，和本地存档**按关卡合并**，再把合并结果推回云端。
3. 推回云端的是**合并后的原始存档**；本机使用的是它再经过 `normalize()` 之后的版本。

设计要点：

- **不认识的关卡和字段不会丢**：`normalize()` 只保留当前版本认识的内容，这一点不用改。保留是在云端那份上做的：每次同步都用本地存档和**云端原始存档**合并，本地没有的关卡或字段（比如只有更新版本才有的），沿用云端的。所以旧版本设备只是看不到这些进度，不会把它们从云端删掉。
- **先验证，再比较**：合并成绩时，先用题目验证两边的方案，只在通过的方案里比较，无效方案不会因为指标看起来更好而被留下。本机代码验证不了的（不认识的关卡或修订号），原样保留云端的，不做判断。
- **“哪份更新”由同步层自己记录**：存档里没有修改时间，时间信息由同步层记在自己的数据里，不需要在存档里加字段。接入前端后，在保存入口按关卡记下修改时间；没有逐关时间的数据（比如设备第一次同步时本地已有的进度），按整份存档的时间判断。不同设备的时钟可能有偏差，所以“以较新的为准”只用于编辑现场、上次所在关、上次查看的章节，它们只影响继续游戏的位置，不影响成绩。
- **出错能恢复**：服务端为每个同步码保留最近若干个版本；同步层在应用云端进度前，也会在本机留一份同步前的存档。

同步依赖 @aliezXDD 代码里的这几样东西：

- **存档结构**：`progress.mjs` 的 `fresh()`、`normalize()`、`recordAttempt()`，以及 `session.mjs` 的 `save()` 用到的字段（第二部分）；
- **关卡 ID 和修订号**；
- **当前题目和历史题目**：`levels.mjs`、`refinements.mjs`、`legacyLevelById`；
- **判定结果**：`evaluate()` 对同一个方案给出的结论；
- **评优行为**：`recordAttempt()` 只在新方案更好时才替换最佳方案（第四部分）。

@HenryShiBinLe 保证：除了第六部分的前端接入，不改 @aliezXDD 的文件，不改玩法、判定、关卡和界面；同步不会因为两台设备版本不同而删掉云端的进度。

## 二、当前存档结构（双方的接口）

```js
{
  version: 1,
  records: {
    "<关卡 ID>": { revision, best, bestMetric, legacyBest, legacy,
                   passed, perfect, attempts, hintUnlocked, state }
  },
  last, chapter, summaries, briefings,
  settings: { sound, volume, motion, speed }
}
```

| 字段 | 含义 | 同步时怎么合并 |
|---|---|---|
| `version` | 存档格式版本，现在是 1 | 两边必须相同。云端版本更高时，旧版本设备暂停同步，不覆盖云端 |
| `records[ID].revision` | 这条记录对应的题目修订号 | 两边不同时，以修订号高的那份记录为准，它的 `best` 和 `state` 对应当前题目；修订号低的那份里的成绩，作为 `legacyBest` 的候选，交给 `normalize()` 按旧题验证 |
| `records[ID].best` | 当前题目下的最佳方案 | 修订号相同时，先用当前题目验证两边方案，再在通过的方案里取更优（直接复用 `recordAttempt()` 的判断，见第四部分） |
| `records[ID].legacyBest` | 按旧题验证通过的旧成绩 | 先按旧题验证，再取更优的一份 |
| `records[ID].state` | 未完成的编辑现场 | 以较新的一份为准 |
| `records[ID].attempts` | 有效运行次数（教学关不计） | 取较大 |
| `records[ID].hintUnlocked` | 策略提示入口是否已解锁 | 任一为真即为真 |
| `records[ID].passed`、`perfect`、`bestMetric`、`legacy` | 是否通过、是否完美（徽记）、最佳指标、是否只有旧版成绩 | 不参与合并，由 `normalize()` 根据 `best` 和 `legacyBest` 重新算出 |
| `last` | 上次所在的关卡 | 以较新的一份为准 |
| `chapter` | 上次查看的章节 | 以较新的一份为准 |
| `summaries` | 已展示过章末总结的章节 | 取并集 |
| `briefings` | 已确认过章节目标的章节 | 取并集 |
| `settings` | 音效、音量、减少动态效果、回放速度 | 不同步（跟随设备） |

说明：

- **修订号不同时的处理**，和 `normalize()` 在单台设备上读档迁移的逻辑一致：旧答案不套到新题上，按旧题验证通过的保留“通过”和“徽记”。合并只是把它推广到两台设备之间。
- **上次所在关、上次查看的章节跨设备同步**：换一台设备继续玩，会接着上次那一关。`last` 指向本机不认识的关时，`normalize()` 会退回默认值。
- **表里没有的字段**（以后新增的）：不会丢，默认以较新的一份为准。

## 三、需要 @aliezXDD 注意的 6 条

### 1. 已发布的关卡 ID 不改

**现状**：存档以关卡 ID 为键（如 `01-02.3`），现有 49 个 ID 保持稳定。ID 由 `levels.mjs` 的 `add()` 按“单元 + 单元内序号”自动生成，`levelTitles` 也按单元内的位置对应标题；`tests/` 和 `scripts/` 里有 120 处直接写了关卡 ID。

**风险**：在单元中间插入一关，后面所有小关的序号都会顺移。玩家的本地进度和云端进度都会对到错误的关卡上，测试也会大面积失败。

**要求**：
- 新关只追加到单元末尾。
- 删除关卡时，不要让后面的关顺移上来（保留占位，或给后面的关写死 ID）。
- 确实要调整顺序时，先和 @HenryShiBinLe 商量，加一张“旧 ID → 新 ID”的映射，让老存档能迁过来。

### 2. 已发布的题，要改判定相关的内容就升修订号

**现状**：改版关卡由 `refinements.mjs` 的 `update()` 设为修订号 2，现在共 22 关，其余 27 关是修订号 1；`legacyLevelById` 保存原始题目（修订号 1）。读档时，旧的最佳方案先按旧题验证，通过的保留“通过”和“徽记”（存为 `legacyBest`），编辑现场清空，旧答案不会被当成新题的答案。@HenryShiBinLe 验证过：这 22 关用原题答案的存档，读档后都作为旧版成绩保留了“通过”。

**哪些改动算“改题”**：会改变判定结果的改动，包括节点和边的增删、权重、起点和终点、预算和各种上限、判定条件，以及 `evaluate()` 里某类题的判定逻辑（它会影响这一类的所有关）。只改坐标、线路弯曲、文案、标题、提示不算改题，随时可以原地改。

**什么算发布**：发给别人玩的包或链接，以及提交作品；团队内部测试用的部署不算。修订号 1 的题视为已发布，旧发布包和现有的旧存档迁移都以它为准。修订号 2 的题目前还没有发布。每次发布，在 `GAMEPLAY_CHANGES.md` 记一笔发布基线（日期、提交号）。

**要求**：
- **已发布的题要改题**：升修订号，不能原地改。原地改的话，玩家存档里的答案会被拿到改过的题上重新评估，也就是把旧答案套到新题上。同一关的同一个修订号永远对应同一道题。修订号 1 的 27 关现在要改题，同样要升到 2。
- **尚未发布的修订号**（现在是 2）：可以继续原地改，直到下一次发布。
- **同一关第一次升到 3 之前**：先把历史题目按修订号保存，旧成绩也要能对应到它的修订号（具体做法由 @aliezXDD 定），并补迁移测试。否则按现在的 `normalize()`，修订号 2 的成绩要么被忽略（已有 `legacyBest` 时），要么被拿去按修订号 1 的题目验证，大概率判为无效。
- 哪些关升了修订号，记在 `GAMEPLAY_CHANGES.md`。

**自动检查**：每次发布时，@HenryShiBinLe 用 `solution()` 为每关生成一份参考答案，连同关卡 ID、修订号和判定结果存成发布基线，并在 `tests/` 里加一个测试。之后 `npm test` 会检查三件事：
- 已发布的修订号下，参考答案的判定结果不变；
- 修订号升了的关，旧修订号的题目仍然找得到；
- 已发布的关卡 ID 都还在。

测试失败，说明改到了已发布的题，需要升修订号或撤回改动。现在 49 关的 `solution()` 都能通过，非教学关都能达到完美，可以直接用作参考答案。

### 3. 存档结构变化要升版本并写迁移

**现状**：顶层是 `version: 1`。Electron 端的 `desktop/storage.cjs` 只接受版本 1，并限制大小在 4 MB 以内，同步服务端沿用同样的检查。

**要求**：
- **新增字段**：在 `fresh()` 里给默认值（或允许缺省），在 `normalize()` 里校验，不需要升版本。
- **修改已有字段的含义或结构**：升到 `version: 2`，在 `normalize()` 里写 1 → 2 的迁移，并告诉 @HenryShiBinLe。服务端的校验和合并规则要跟着改。
- 存档里只放进度和设置，不放截图、回放帧等大块数据。同步时整份上传，越小越好。

### 4. 新增存档字段时，说明它怎么同步

**要求**：新增存档字段时，在 `GAMEPLAY_CHANGES.md` 里注明它属于哪一类：
- **累积型**：取更优、取较大或取并集，如 `best`、`attempts`、`summaries`；
- **现场型**：以较新的为准，如 `state`、`last`；
- **本机型**：不同步，如 `settings`；
- **派生型**：由 `normalize()` 算出，不参与合并，如 `passed`、`perfect`。

没注明的字段默认按“以较新的一份为准”处理，不会丢，但可能合并得不够理想。

### 5. 判定保持确定性

**现状**：`normalize()` 读档时会用题目重新评估存档里的 `best` 和 `legacyBest`，再算出“通过”和“完美”。这一步校验的是存档里的答案是否有效，不能防止玩家直接填入合法答案或修改尝试次数。同步合并之后，每台设备也会这样重新评估一遍，所以同一份存档在不同设备上必须得出相同的结果。

**要求**：`evaluate()` 必须是确定性的：同一题目、同一状态，在任何设备上的结果都相同。不要用随机数、当前时间、屏幕尺寸等会变化的值参与判定。现在的规则代码满足这一点，请保持。

### 6. 规则和存档模块保持能在 Node 里运行

**现状**：合并逻辑和它的测试在 Node 里运行，会直接调用 `fresh()`、`normalize()`、`recordAttempt()`，进而用到 `levels`、`refinements`、`solids`、`solid-nets`、`briefs`、`engine`、`algorithms`、`replays` 这些模块。现有 87 项测试就是在 Node 里导入它们的，全部通过。

**要求**：
- 这些模块里不要使用 `window`、`document`、`localStorage`、Canvas 等浏览器专属的东西。界面相关的代码放在 `main.mjs`、`board.mjs` 等界面文件里。
- 保持 `normalize()` 的用法：传入一份存档，返回一份合法存档；遇到异常数据尽量清洗，而不是抛错。
- 保持 `normalize()` 幂等：对它的输出再整理一次，结果不变。否则每次读档或同步，存档都会变一点，两台设备之间会来回改。现在满足，@HenryShiBinLe 在 400 份构造的存档上验证过，会加成测试。
- 同步侧调用 `normalize()` 时会加一层兜底：出错就保留本地存档，不覆盖云端。目前用约 1.3 万份随机构造的异常存档抽样试过，`normalize()` 没有抛错；@HenryShiBinLe 会补异常输入的测试。

## 四、评优规则：只在 `recordAttempt()` 里维护

同一修订号下，两台设备可能各有一份最佳方案，合并时要留下更好的那份。“通过”和“完美”由 `normalize()` 根据最佳方案算出，留错了，玩家的最好成绩就会变差。

判断规则现在写在 `recordAttempt()` 里：还没有最佳方案时直接记录；新方案完美而旧方案不完美时替换；否则比指标（二分图匹配越大越好，其他题型越小越好）。

合并逻辑不另抄这套规则，而是直接复用 `recordAttempt()`：先用题目验证两边方案，再在一份临时存档上把方案 A 设为最佳，用方案 B 调用一次，看最佳方案有没有被换成 B。比较旧版成绩时，传入旧题即可。这样 @aliezXDD 以后改评优规则，合并会自动跟着变，也不需要为同步改任何代码。

**要求**：保持 `recordAttempt()` 现在的行为：只有新方案更好时才替换 `best`；只修改传入的存档对象，不碰界面，也不读写存储。

## 五、协作方式

**记录**：改关、修订号、存档字段的变化，写在 `GAMEPLAY_CHANGES.md` 的“存档兼容”部分，写清哪些关升了修订号，新增了哪些字段、属于哪一类；每次发布也在这里记一笔发布基线。@HenryShiBinLe 会看这份文档决定合并规则和服务端要不要跟着改。

**目录**：@HenryShiBinLe 只新增 `server/`（同步服务端）、`src/sync/`（合并逻辑），以及 `tests/` 里以 `sync` 开头的测试文件。除了第六部分约好的前端接入，不改 @aliezXDD 的文件。

**分支**：都在 `main` 上开发，较大的改动用短期功能分支，1～2 天内合回。推送前跑通 `npm test` 和 `npm run build`。

## 六、前端接入（时间另行商量）

**接入范围**：只做三处。
1. 读档、存档的入口接上同步：`main.mjs` 里直接读写存档的地方，改为经过同步层；
2. 设置里加同步入口：生成或输入同步码，查看同步状态；
3. 同步拉到新进度后，应用到界面。

**应用云端进度的方式**：沿用导入存档（`importSave()`）现有的处理方式，即停止播放、清空会话缓存 `sessionCache`、替换存档、保存、重画；并且只在玩家不在关卡里时执行，在关卡里时等退出后再应用。原因是缓存的关卡会话持有旧存档对象的引用，直接替换存档，之后的操作会写进旧对象里丢掉。以后如果新增持有存档引用的缓存，也要在这一处一起清掉。

**导入存档**：接入同步后，导入的进度会合并进云端，不会删掉云端已有的进度。想从头开始，换一个新的同步码。

**接入方式**：开始前 @aliezXDD 先推送；接入期间 @aliezXDD 暂停修改 `main.mjs` 和设置弹窗；@HenryShiBinLe 改完立即推送，@aliezXDD 拉取后继续。具体时间两人另外商量。

**桌面版**：`desktop/main.cjs` 会拦截所有网络请求，这是安全设计，保持不变。桌面版暂不接同步，可以继续用导出和导入。

其他前端事项，包括 Web 部署、Mac 外壳、浏览器兼容、字体、快捷键等平台适配，暂不提要求，等前端稳定后再商量。
